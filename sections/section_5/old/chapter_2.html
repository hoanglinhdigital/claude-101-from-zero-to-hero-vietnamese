6. Claude cho Tester / QA / Kỹ thuật prompt sinh test case bao phủ đầy đủ

Giới thiệu

Một bộ test case tốt cần bao phủ đủ 3 nhóm case: happy path (luồng chính, input hợp lệ), edge case (giá trị biên, tình huống hiếm gặp) và negative case (input sai, hệ thống phải từ chối đúng cách). Nếu prompt chỉ yêu cầu chung "sinh test case cho chức năng X", Claude thường có xu hướng tập trung vào happy path và bỏ sót edge/negative case. Chương này trình bày kỹ thuật viết prompt để chủ động yêu cầu Claude bao phủ đủ cả 3 nhóm, minh hoạ xuyên suốt bằng chức năng "tạo khoản chi tiêu" của app Quản lý chi tiêu (Expense Management) đã xây dựng ở Section 4.

Các tính năng chính

  • Happy path — test case với input hợp lệ, đi đúng luồng nghiệp vụ chính, kết quả mong đợi là thành công.
  • Edge case — test case với giá trị ở biên (nhỏ nhất, lớn nhất, đúng ngay ranh giới hợp lệ/không hợp lệ) hoặc tình huống ít xảy ra nhưng vẫn hợp lệ.
  • Negative case — test case với input sai, vi phạm ràng buộc nghiệp vụ, kết quả mong đợi là hệ thống báo lỗi đúng cách (không phải crash hay lưu sai dữ liệu).
  • Prompt hiệu quả nên liệt kê rõ từng ràng buộc của requirement (thay vì mô tả chung), và yêu cầu tường minh Claude phải sinh đủ cả 3 nhóm — không để Claude tự quyết định phạm vi bao phủ.
  • Nên yêu cầu Claude trình bày test case theo dạng table chuẩn (Ví dụ: No, Mô tả, Bước thực hiện, Dữ liệu vào, Kết quả mong đợi) để dễ review và đưa vào bộ test chính thức.

Bảng phân loại test case — ví dụ "Tạo khoản chi tiêu"

Requirement: "Tạo khoản chi tiêu — số tiền phải > 0, ngày chi tiêu có thể ở tương lai, phải chọn Account và Category có sẵn, description có thể bỏ trống,..."

NhómĐịnh nghĩaVí dụ cho chức năng "Tạo khoản chi tiêu"
Happy path Input hợp lệ, đi đúng luồng chính, không vi phạm ràng buộc nào. amount = 150000, spentAt = hôm nay, categoryId = category có sẵn → lưu thành công.
Edge case Giá trị nằm đúng ranh giới hợp lệ/không hợp lệ, hoặc trường hợp hợp lệ nhưng hiếm gặp. amount = 0.01 (nhỏ nhất > 0); spentAt = đúng thời điểm hiện tại (biên giữa "hiện tại" và "tương lai").
Negative case Input vi phạm ràng buộc, hệ thống phải từ chối rõ ràng, không lưu dữ liệu sai. amount = -50000 hoặc = 0; categoryId hoặc accountId không tồn tại trong hệ thống.
Mẹo: Sau khi Claude sinh xong bộ test case, luôn hỏi thêm một câu rà soát: "Rà soát lại bộ test case vừa sinh — còn thiếu case nào thuộc 3 nhóm trên, hoặc case nào liên quan đến kết hợp nhiều ràng buộc cùng lúc không (vd amount âm VÀ ngày tương lai cùng lúc)?". Câu hỏi rà soát thường giúp phát hiện thêm 2-3 case bị bỏ sót.

Use Cases

Thiết kế test case cho tính năng mới

Chuyển requirement thành bộ test case đầy đủ 3 nhóm trong vài phút, thay vì tự liệt kê thủ công dễ bỏ sót.

Review lại test suite hiện có

Đưa bộ test case đang có cho Claude, hỏi "case nào thuộc nhóm nào, còn thiếu nhóm nào" để tự đánh giá độ bao phủ.

Chuẩn hoá format test case toàn team

Yêu cầu Claude luôn xuất ra đúng bảng chuẩn (No, Mô tả, Bước thực hiện, Dữ liệu vào, Kết quả mong đợi) để đồng nhất giữa các Tester.

Thông tin bổ sung

Chất lượng test case Claude sinh ra phụ thuộc trực tiếp vào độ rõ ràng của requirement đưa vào. Nếu requirement chỉ nêu "số tiền phải hợp lệ" mà không nói rõ "hợp lệ" nghĩa là gì (> 0? có giới hạn tối đa?), Claude sẽ phải tự suy diễn — dẫn đến test case có thể sai lệch với ý định thật của Product Owner. Luôn làm rõ ràng buộc trước khi generate, và xem lại từng case trước khi đưa vào bộ test chính thức.
