11. Harness Engineering / Guides & Sensors: feedforward và feedback trong thiết kế Harness

Giới thiệu

Mọi cơ chế kiểm soát trong một harness đều thuộc một trong hai nhóm: Guides (điều khiển trước khi agent hành động — "feedforward") và Sensors (điều khiển sau khi agent hành động — "feedback"). Cách phân loại này, được Birgitta Böckeler (Thoughtworks) trình bày trên martinfowler.com, mượn từ điều khiển học (cybernetics): muốn hệ thống ổn định cần vừa định hướng trước vừa đo và hiệu chỉnh sau. Hiểu hai nhóm này giúp bạn biết nên thêm loại kiểm soát nào cho từng loại lỗi.

Các tính năng chính

  • Guides (feedforward): tăng xác suất agent làm đúng ngay lần đầu — CLAUDE.md, tài liệu kiến trúc, Skill, ví dụ mẫu, template.
  • Sensors (feedback): phát hiện và đưa sai sót trở lại cho agent tự sửa — typecheck, lint, test, kiểm tra kiến trúc, review bằng AI.
  • Computational (tính toán): kiểm soát bằng code, kết quả xác định, chạy nhanh và rẻ — thường dùng làm "cổng cứng".
  • Inferential (suy luận): kiểm soát bằng LLM (review ngữ nghĩa, LLM-as-judge) — linh hoạt với tiêu chí mềm nhưng chậm hơn, tốn hơn và không hoàn toàn nhất quán.
  • Vòng lặp tự sửa: thông báo lỗi của sensor được trả lại model (qua Hook exit code 2) để model tự khắc phục — gọi là "backpressure".

Guides làm giảm số lần agent đi sai; Sensors bắt phần sai còn lại và đẩy ngược về cho agent (nét đứt). Hai nhóm bổ sung cho nhau: chỉ có Guides thì agent có thể bỏ qua; chỉ có Sensors thì agent phải thử–sai nhiều lần, tốn token.

Nguyên tắc thiết kế harness

  • Bản đồ, không phải cuốn bách khoa: giữ CLAUDE.md ngắn (vài chục dòng), trỏ tới docs/ cho chi tiết. Một file hướng dẫn quá dài bị bỏ sót và khó kiểm tra còn đúng hay không.
  • Ưu tiên ép buộc bằng code: điều gì quan trọng và kiểm tra được bằng máy thì viết thành sensor. Guide bằng chữ chỉ là lời nhắc; sensor mới là cổng chặn.
  • Thông báo lỗi dành cho agent: nêu file, dòng, quy tắc bị vi phạm và cách sửa. Lỗi mơ hồ khiến agent đoán mò.
  • Phản hồi nhanh và rẻ trước: chạy sensor computational (vài giây) trước sensor inferential (tốn token). Chỉ chạy test nặng ở bước cuối (Stop).
  • Bắt đầu tối thiểu, thêm khi có bằng chứng: mỗi rule mới phải xuất phát từ một lỗi lặp lại thật, không phải phỏng đoán.
  • Rà soát và loại bỏ: model mới có thể không cần một số rule cũ. Harness phình to là gánh nặng chi phí và nguồn gây hành vi lạ.

Use Cases

Giữ ranh giới kiến trúc

Guide: ghi quy tắc phân tầng và ví dụ đúng/sai trong docs/ARCHITECTURE.md. Sensor: script quét import, chặn UI gọi thẳng database — chính là bài lab ở chương sau.

Chống "tuyên bố xong quá sớm"

Hook Stop chạy test trước khi cho agent kết thúc. Nếu test fail, agent phải tiếp tục sửa thay vì báo cáo hoàn thành — loại bỏ lỗi "nói xong nhưng chưa chạy được".

Review thiết kế bằng sensor inferential

Với tiêu chí khó viết thành code (đặt tên, độ dễ hiểu), dùng Sub-agent reviewer đọc diff và nhận xét theo checklist — kết hợp với sensor computational để có cả độ chắc chắn lẫn độ linh hoạt.

Thông tin bổ sung

Rủi ro thường gặp:
  • Vòng lặp vô hạn: sensor luôn fail khiến agent sửa mãi. Cần cơ chế ngắt (ví dụ kiểm tra cờ stop_hook_active ở Hook Stop) và giới hạn số lượt.
  • Agent "lách" sensor: sửa hoặc xoá test cho pass. Giảm nguy cơ bằng rule rõ ràng trong guide, review diff và hạn chế quyền sửa file test/cấu hình lint.
  • Sensor quá chậm: chạy full test sau mỗi lần sửa file làm phiên làm việc chậm và tốn tiền. Phân tầng: nhanh sau mỗi lần sửa, nặng ở cuối.
  • Quá ràng buộc: quá nhiều rule khiến agent kém linh hoạt và khó đạt kết quả tốt. Cân bằng giữa an toàn và tự chủ.
  • Chi phí: sensor computational gần như miễn phí so với token; sensor inferential tốn thêm lượt gọi model — chỉ dùng ở điểm kiểm soát quan trọng.
  • An toàn: script sensor là code chạy với quyền của bạn; luôn review trước khi thêm vào settings.json (xem Section 9).
