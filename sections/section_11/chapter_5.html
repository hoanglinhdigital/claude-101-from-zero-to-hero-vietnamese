11. Harness Engineering / Lab 1 - Chỉ dùng Prompt Engineering
Lab 1 / 8 — chỉ có Prompt. Tiếp nối Lab trước (project D:\lab-realestate, tag scaffold). Ở giai đoạn này chưa có CLAUDE.md, Hook, Skill hay kiểm tra tự động nào — agent chỉ có prompt của bạn. Mục tiêu là cảm nhận giới hạn của Prompt Engineering trước khi thêm harness.

Mục tiêu

  • Chạy cùng một yêu cầu bằng prompt sơ sài và prompt có cấu trúc (vai trò, bối cảnh, nhiệm vụ, ràng buộc, cách làm, tiêu chí xong) rồi so sánh bằng scorecard.ps1.
  • Xây dựng chức năng đầu tiên: đăng nhập/đăng xuất và đăng tin theo role.
  • Nhận ra điểm yếu cố hữu của "chỉ có prompt": phải lặp lại mọi quy tắc ở mỗi lần hỏi, không có bộ nhớ giữa các phiên, không có cơ chế kiểm tra tự động.

Cùng một agent, cùng một điểm xuất phát (tag scaffold), chỉ khác prompt. Mỗi kết quả nằm trên một nhánh riêng để đo và so sánh độc lập.

Yêu cầu trước khi bắt đầu

  • Hoàn thành Lab "Khởi tạo project": có tag scaffold, container realestate-db đang chạy, scorecard.ps1 hoạt động.
  • Working tree sạch (git status --short không in gì).

Các bước thực hành

  1. Bước 1: Thí nghiệm A — prompt sơ sài

    Tạo nhánh từ điểm mốc và chạy Claude Code ở chế độ tự chấp nhận sửa file để quan sát toàn bộ quá trình:

    cd D:\lab-realestate
docker compose up -d db
git switch main
git switch -c lab1-weak scaffold
claude --permission-mode acceptEdits
    Làm chức năng đăng nhập và đăng tin cho web bất động sản.

    Khi Claude Code xong (có thể hỏi lại bạn vài câu — hãy trả lời ngắn gọn theo ý hợp lý), thoát bằng /exit rồi đo và lưu lại:

    powershell -NoProfile -ExecutionPolicy Bypass -File scorecard.ps1 -Label lab1-weak
git add -A
git commit -m "lab1-weak: ket qua voi prompt so sai"
  2. Bước 2: Thí nghiệm B — prompt có cấu trúc

    Quay về điểm xuất phát, tạo nhánh mới và dán prompt sau (đây là yêu cầu giống hệt về nội dung nhưng được mô tả đầy đủ):

    git switch main
git switch -c lab1-strong scaffold
claude --permission-mode acceptEdits
    Vai trò: bạn là senior full-stack developer chuyên Next.js (App Router) + TypeScript + Prisma.

Bối cảnh: project lab-realestate là website bất động sản. Đã có schema Prisma (User, Listing, SystemSetting), Prisma client ở src/lib/prisma.ts, và đã cài sẵn bcryptjs, jose, zod. Có 4 role: BUYER (người mua), SELLER (người bán), MODERATOR (quản trị viên duyệt tin), SYSTEM_ADMIN. Tài khoản mẫu: seller@demo.vn, buyer@demo.vn, mod@demo.vn, admin@demo.vn, mật khẩu chung Passw0rd!.

Nhiệm vụ: làm 2 chức năng.
1) Đăng nhập/đăng xuất bằng email + mật khẩu (bcryptjs). Session lưu trong cookie httpOnly chứa JWT ký bằng jose với biến môi trường AUTH_SECRET. Tài khoản isActive=false không đăng nhập được. Có trang /login và nút đăng xuất.
2) Đăng tin tại trang /listings/new: SELLER chỉ được tạo tin type=SALE, BUYER chỉ được tạo tin type=WANTED, các role khác không được đăng. Tin mới có status=PENDING. Form gồm title, description, propertyType, priceMillion, areaM2, city, district; validate bằng Zod ở phía server. Thêm trang /listings hiển thị các tin có status=APPROVED.

Ràng buộc: không sửa prisma/schema.prisma; không thêm thư viện mới; TypeScript strict, không dùng any; thông báo lỗi hiển thị cho người dùng bằng tiếng Việt.

Cách làm: lập kế hoạch ngắn trước rồi mới code. Khi xong, tự chạy npm run typecheck và npm run lint, sửa lỗi nếu có và báo kết quả.

    Khi xong, thoát /exit, đo và lưu:

    powershell -NoProfile -ExecutionPolicy Bypass -File scorecard.ps1 -Label lab1-strong
git add -A
git commit -m "lab1-strong: ket qua voi prompt co cau truc"
  3. Bước 3: So sánh hai nhánh 
    Import-Csv scoreboard.csv | Format-Table label, typecheck, lint, tests, test_files, ui_db_imports, any_usage
git diff --stat scaffold lab1-weak -- src | Select-Object -Last 1
git diff --stat scaffold lab1-strong -- src | Select-Object -Last 1

    Chỉ số thường thấy: prompt có cấu trúc cho kết quả đúng yêu cầu hơn (đúng role, có validate, ít any hơn), nhưng tests vẫn NONE và ui_db_imports thường khác 0 vì bạn chưa yêu cầu kiểm thử hay tách tầng. Kết quả của AI không cố định giữa các lần chạy — hãy ghi lại số liệu của bạn.

  4. Bước 4: Kiểm tra chức năng trên nhánh lab1-strong 
    npm run dev

    Mở http://localhost:3000/login và thử lần lượt:

    • Đăng nhập seller@demo.vn / Passw0rd! → vào /listings/new → đăng tin → tin ở trạng thái chờ duyệt (không hiện ở /listings).
    • Đăng nhập buyer@demo.vn → chỉ đăng được tin cần mua; thử gửi tin loại bán phải bị từ chối.
    • Đăng nhập mod@demo.vn → truy cập /listings/new phải bị từ chối.

    Dừng server (Ctrl+C) sau khi thử xong. Ghi lại những chỗ chưa đúng — đó là dữ liệu quý cho các Lab sau.

  5. Bước 5: Thí nghiệm C — phiên mới, prompt ngắn (thấy rõ giới hạn)

    Agent không nhớ gì từ phiên trước. Mở phiên mới trên nhánh lab1-strong và đưa một yêu cầu ngắn, như cách người ta thường làm trong thực tế:

    git switch -c lab1-short lab1-strong
claude --permission-mode acceptEdits
    Thêm trang chi tiết tin /listings/[id], hiển thị đầy đủ thông tin của tin đã duyệt.
    powershell -NoProfile -ExecutionPolicy Bypass -File scorecard.ps1 -Label lab1-short
git add -A
git commit -m "lab1-short: prompt ngan trong phien moi"
Select-String -LiteralPath "src\app\listings\[id]\page.tsx" -Pattern "prisma|requireRole|role" -ErrorAction SilentlyContinue

    Quan sát: agent có tự phát minh cách truy cập dữ liệu mới (ví dụ gọi Prisma trực tiếp trong trang) thay vì tái sử dụng cách đã dùng ở nhánh trước? Chỉ số ui_db_imports có tăng không?

  6. Bước 6: Chọn nhánh làm nền cho các Lab sau

    Giữ lại kết quả của prompt có cấu trúc (chức năng đăng nhập/đăng tin) làm nền. Nhánh lab1-short giữ lại để đối chiếu, không hợp nhất.

    git switch main
git merge --ff-only lab1-strong
git tag lab1-done
git log --oneline -3

✅ Kết quả mong đợi

Bạn có ba dòng điểm (lab1-weak, lab1-strong, lab1-short) trong scoreboard.csv. Prompt có cấu trúc giúp kết quả đúng hơn trong lần đó, nhưng khi sang phiên mới với yêu cầu ngắn, chất lượng và cách làm lại không nhất quán; chưa có test, chưa có tầng tách biệt, chưa có kiểm tra nào chạy tự động. Nhánh main đã chứa chức năng đăng nhập/đăng tin để dùng cho Lab tiếp theo.

Rút ra: Prompt Engineering mạnh nhưng nằm trong từng lượt hỏi — nó không tự tích luỹ. Ba điểm yếu cần harness giải quyết: (1) quy tắc phải được lặp lại mãi → cần Context bền vững; (2) không có người kiểm tra → cần Sensor; (3) không nhớ giữa các phiên → cần Memory/State.

Troubleshoot

Lỗi: Đăng nhập báo lỗi kết nối cơ sở dữ liệu khi chạy thử.
Nguyên nhân: Container PostgreSQL chưa chạy.
Giải pháp: docker compose up -d db rồi docker compose ps để chắc chắn healthy.
Lỗi: Cả hai nhánh cho kết quả gần như giống nhau.
Nguyên nhân: Với yêu cầu nhỏ, model mạnh có thể tự suy luận tốt; kết quả cũng có tính ngẫu nhiên.
Giải pháp: Hãy chạy lại thí nghiệm vài lần hoặc để ý các chỉ số khác (any_usage, số file thay đổi, cách tổ chức thư mục). Điều quan trọng là bạn có số liệu để so sánh, không phải con số "đẹp".
Lỗi: scorecard.ps1 báo FAIL ở typecheck hoặc lint trên nhánh vừa tạo.
Nguyên nhân: Code agent tạo ra có lỗi — đây chính là dữ liệu của thí nghiệm.
Giải pháp: Ghi nhận kết quả, không cần tự sửa. (Riêng nhánh lab1-strong: nếu còn lỗi, nhờ Claude Code sửa trước khi hợp nhất vào main.)
