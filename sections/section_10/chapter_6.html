10. Phát triển phần mềm với Spec-Kit Framework / Lab - Implement, đối chiếu & sửa bug
Bài lab này tiếp tục dùng project D:\lab-codekids-blocks và tasks.md của tính năng "kéo thả khối lệnh vượt mê cung" đã tạo ở Chapter 5. Đây là bài lab khép lại vòng SDD bằng giai đoạn Implementation và Convergence, đồng thời xử lý bug thực tế phát sinh sau Convergence (lỗi giao diện kéo thả) bằng bộ công cụ /speckit-bug-assess và /speckit-bug-fix — Chapter 7 tiếp theo sẽ triển khai sản phẩm hoàn chỉnh này lên Vercel và TiDB.

Mục tiêu

  • Dùng /speckit-implement để Claude Code triển khai lần lượt các task đã chia ở tasks.md.
  • Theo dõi tiến độ thực thi từng task, xác nhận từng bước trước khi cho phép ghi file.
  • Kiểm chứng màn chơi kéo thả vượt mê cung chạy đúng thực tế trên trình duyệt sau khi implement xong.
  • Dùng /speckit-converge để Claude Code tự đối chiếu kết quả thực tế với spec.md ban đầu — xác nhận không thiếu, không lệch yêu cầu.
  • Dùng /speckit-bug-assess và /speckit-bug-fix để chẩn đoán và sửa các bug phát sinh khi thử nghiệm thực tế mà spec.md chưa mô tả đủ chi tiết để /speckit-converge phát hiện ra.

Claude Code thực thi tuần tự từng task trong tasks.md, đánh dấu hoàn thành ngược lại vào file này. Sau khi hết task và kiểm chứng thủ công trên trình duyệt, chạy /speckit-converge để Claude Code tự đối chiếu toàn bộ kết quả với spec.md gốc — lặp lại cặp implement/converge cho đến khi báo cáo xác nhận Converged, khép vòng SDD cho tính năng lõi của CodeKids Blocks.

Yêu cầu trước khi bắt đầu

  • Đã hoàn thành Chapter 5 — specs/{feature-id}/plan.md và tasks.md đã có nội dung chi tiết, đủ nhỏ để implement từng phần.
  • Docker Desktop đang chạy, MySQL container (codekids-mysql) đã khởi động lại nếu trước đó đã docker compose down.
  • Claude Code CLI đã cài đặt và đăng nhập thành công.
  • Terminal: PowerShell hoặc Windows Terminal.

Các bước thực hành

Phần 1: Triển khai bằng /speckit-implement

  1. Bước 1: Khởi động lại MySQL container và Claude Code 
    cd D:\lab-codekids-blocks
docker compose up -d
claude
  2. Bước 2: Chạy /speckit-implement để bắt đầu triển khai

    Claude Code sẽ đọc tasks.md và thực thi lần lượt từng task theo đúng thứ tự đã chia ở Chapter 5.

    /speckit-implement
  3. Bước 3: Theo dõi và xác nhận từng task

    Ở mỗi task (cập nhật schema.prisma, tạo lib/maze-engine.ts, viết unit test, tạo API route, thêm UI kéo thả...), đọc qua thay đổi được đề xuất trước khi xác nhận cho ghi file — đặc biệt chú ý logic trong lib/maze-engine.ts vì đây là phần chấm điểm chính thức, ảnh hưởng trực tiếp đến tính công bằng của trò chơi.

  4. Bước 4: Chạy migration Prisma khi task tạo/sửa schema.prisma hoàn tất 
    npx prisma migrate dev --name add_level_player_progress
  5. Bước 5: Chạy unit test sau khi các task liên quan lib/maze-engine.ts hoàn tất

    Tự chạy lại test độc lập, không chỉ tin vào báo cáo "đã pass" của Claude Code.

    npm test
PASS  __tests__/maze-engine.test.ts
  runProgram
    ✓ nhân vật đến đúng ô đích khi chuỗi lệnh hợp lệ
    ✓ dừng lại và báo va chạm khi đi vào ô tường
  6. Bước 6: Chờ Claude Code hoàn thành toàn bộ task và báo cáo tổng kết

    Sau khi hết task trong tasks.md, đọc lại tổng kết các file đã tạo/sửa trước khi qua bước kiểm chứng thực tế.

Phần 2: Kiểm chứng thực tế và Convergence với /speckit-converge

  1. Bước 7: Khởi động dev server và thử màn chơi trên trình duyệt 
    npm run dev

    Mở http://localhost:3000, nhập một biệt danh bất kỳ, kéo các khối lệnh (Đi tới, Rẽ trái, Rẽ phải, Lặp lại) vào khung làm việc ở màn 1, bấm "Chạy" và xác nhận nhân vật di chuyển từng bước đúng theo chuỗi lệnh đã ghép, đến đích thì hiển thị số sao đạt được.

  2. Bước 8: Thử trường hợp va chạm và chưa hoàn thành

    Ghép một chuỗi lệnh cố tình khiến nhân vật đi vào tường — xác nhận trò chơi dừng đúng vị trí va chạm, hiển thị thông báo thân thiện (không dùng từ "Thua"/"Sai") và cho phép sửa lại ngay. Sau đó thử một chuỗi lệnh ngắn hơn cần thiết để xác nhận trường hợp "chưa hoàn thành" (hết lệnh mà chưa đến đích) hiển thị đúng và không lưu kết quả.

  3. Bước 9: Thử màn khó hơn cần dùng khối Lặp lại

    Ở màn có độ khó cao hơn, thử ghép chuỗi lệnh không dùng khối Lặp lại (nhiều khối Đi tới lặp lại thủ công) và so sánh số sao đạt được với khi dùng khối Lặp lại để tối ưu — xác nhận cơ chế chấm sao theo số khối lệnh hoạt động đúng như đã đặc tả.

  4. Bước 10: Chạy /speckit-converge để đối chiếu kết quả với spec.md

    Thay vì tự viết checklist đối chiếu bằng tay, dùng đúng slash command Convergence có sẵn của Spec-Kit — lệnh này tự đọc lại spec.md, so sánh với code hiện tại và kết quả kiểm chứng ở các bước trên.

    /speckit-converge

    Đọc kỹ báo cáo trả về: liệt kê yêu cầu nào trong spec.md đã đáp ứng đầy đủ, yêu cầu nào còn thiếu hoặc chưa đúng (nếu có), kèm vị trí file liên quan, và trạng thái tổng thể (Converged hoặc còn phần lệch).

  5. Bước 11: Xử lý phần chưa khớp (nếu có)

    Nếu báo cáo ở Bước 10 chưa phải Converged, quay lại cập nhật spec.md/plan.md/tasks.md cho đúng thực tế mong muốn (nếu spec sai) hoặc yêu cầu sửa code (nếu implement sai), rồi chạy lại /speckit-implement cho phần liên quan — không sửa tay trực tiếp vào code mà bỏ qua việc cập nhật spec. Lặp lại cặp /speckit-implement → /speckit-converge cho đến khi báo cáo xác nhận Converged.

Phần 3: Xử lý bug phát sinh sau khi Converged bằng /speckit-bug-assess và /speckit-bug-fix

/speckit-converge chỉ đối chiếu code với yêu cầu đã đặc tả trong spec.md — nó không phát hiện những lỗi hành vi thực tế mà spec chưa mô tả đủ chi tiết (ví dụ vùng nhận thả của khối lệnh chưa tính đúng mọi vị trí trong workspace). Đây là lúc dùng đúng bộ công cụ bug fixing riêng của Spec-Kit — /speckit-bug-assess để chẩn đoán, /speckit-bug-fix để sửa — thay vì quay lại /speckit-implement. Bộ công cụ này là extension riêng, chưa có sẵn khi cài Spec-Kit mặc định.
  1. Bước 12: Cài extension bug fixing cho Spec-Kit

    Bộ lệnh /speckit-bug-assess, /speckit-bug-fix không có sẵn khi chạy specify init mặc định ở Chapter 3 — đây là extension riêng, cần cài thêm vào project trước khi dùng.

    cd D:\lab-codekids-blocks
specify extension add bug

    Sau khi cài xong, mở lại phiên Claude Code (/exit rồi chạy lại claude) để slash command mới được nạp — gõ /speckit-bug- để xác nhận thấy gợi ý /speckit-bug-assess và /speckit-bug-fix trước khi qua bước tiếp theo.

  2. Bước 13: Ghi nhận Bug — Không thể kéo block mới vào vị trí dưới cùng

    Mô tả lại đúng hiện tượng và bước tái hiện cho /speckit-bug-assess chẩn đoán trước khi sửa.

    /speckit-bug-assess Khi kéo khối lệnh thứ 2 trở đi từ palette vào workspace, không thể kéo khối lệnh vào bên dưới khối lệnh đã có, bắt buộc phải kéo đè lên khối lệnh đã có sau đó tinh chỉnh lại vị trí. Tái hiện: mở màn bất kỳ 1/2/3 (nhiều khối), kéo một khối bất kỳ sau đó kéo khối thứ 2 rồi thả vào ngay dưới khối thứ nhất, mong đợi khối thứ 2 sẽ nằm dưới nhưng kết quả là khối thứ 2 bị bật trở lại lại palette
  3. Bước 14: Đọc báo cáo chẩn đoán, xác nhận trước khi sửa

    Đọc kỹ phần root cause, file/hàm liên quan và mức độ ảnh hưởng mà /speckit-bug-assess trả về (thường trỏ đúng vào hàm xử lý ondrop — vùng nhận thả (drop zone) chưa tính đúng khoảng trống ngay dưới khối cuối cùng trong workspace). Xác nhận chẩn đoán khớp với hiện tượng đã thấy trên trình duyệt trước khi cho phép sửa.

  4. Bước 15: Chạy /speckit-bug-fix để sửa bug 
    /speckit-bug-fix

    Đọc thay đổi được đề xuất trước khi xác nhận ghi file — đúng phạm vi sửa là cách xác định vùng nhận thả hợp lệ trong workspace, không sửa lan sang logic chấm điểm hay cấu trúc dữ liệu khối lệnh.

  5. Bước 16: Kiểm chứng lại trên trình duyệt

    Lặp lại đúng bước tái hiện ở Bước 13 (kéo khối thứ 2 thả ngay dưới khối thứ nhất) ở cả 3 màn 1/2/3 — xác nhận khối mới nằm đúng vị trí dưới khối đã có ngay lần thả đầu tiên, không còn bị bật trở lại palette.

✅ Kết quả mong đợi

Màn chơi kéo thả khối lệnh vượt mê cung hoạt động đúng với cả 3 kết quả (đến đích, va chạm, chưa hoàn thành), chấm sao đúng theo số khối lệnh đã dùng, chơi được ngay bằng biệt danh không cần đăng nhập. /speckit-converge báo cáo trạng thái Converged, và bug phát sinh khi thử nghiệm thực tế (không kéo thả được khối mới vào đúng vị trí dưới cùng) đã được chẩn đoán bằng /speckit-bug-assess và sửa bằng /speckit-bug-fix, xác nhận lại đúng trên trình duyệt — khép vòng SDD cho tính năng lõi của CodeKids Blocks.

Troubleshoot

Lỗi: /speckit-implement dừng giữa chừng, báo lỗi khi thực thi một task cụ thể.
Nguyên nhân: Task đó phụ thuộc vào một package chưa được cài đặt đúng, hoặc mô tả task chưa đủ rõ so với thực tế project.
Giải pháp: Đọc thông báo lỗi cụ thể, yêu cầu Claude Code cài package còn thiếu (npm install) hoặc làm rõ lại task đó rồi tiếp tục /speckit-implement — các task đã hoàn thành trước đó vẫn được giữ nguyên.
Lỗi: Kéo thả khối lệnh trên trình duyệt bị giật, thả không đúng vị trí trong khung làm việc.
Nguyên nhân: Logic tính vị trí thả (drop) trong component workspace chưa xử lý đúng toạ độ tương đối khi khung làm việc có scroll hoặc padding.
Giải pháp: Yêu cầu Claude Code kiểm tra lại hàm xử lý sự kiện ondrop, tính toạ độ dựa trên getBoundingClientRect() của khung làm việc thay vì toạ độ tuyệt đối trên trang.
Lỗi: Số sao lưu vào database khác với số sao hiển thị trên giao diện.
Nguyên nhân: UI tự tính sao ở client bằng logic riêng thay vì dùng đúng kết quả server trả về từ /api/progress.
Giải pháp: Yêu cầu Claude Code sửa UI để hiển thị đúng số sao lấy từ response của API — chỉ dùng logic client để xem trước hiệu ứng di chuyển, không dùng để tính điểm cuối cùng.
Lỗi: /speckit-converge báo cáo lặp đi lặp lại là chưa Converged dù đã sửa code đúng như spec.
Nguyên nhân: Bản thân spec.md mô tả mơ hồ hoặc thiếu chi tiết ở đúng phần đang bị đối chiếu lệch, khiến Claude Code hiểu sai ý định ban đầu mỗi lần chạy lại.
Giải pháp: Đọc kỹ phần "còn lệch" trong báo cáo, cập nhật trực tiếp câu chữ mơ hồ trong spec.md cho rõ ràng hơn (thay vì chỉ sửa code), rồi chạy lại /speckit-implement → /speckit-converge.
Lỗi: /speckit-bug-assess chỉ ra sai file, hoặc chẩn đoán chung ("có thể do logic drag-drop") không đủ cụ thể để sửa.
Nguyên nhân: Mô tả bug ban đầu thiếu bước tái hiện cụ thể (thiếu màn cụ thể, thiếu đúng thứ tự thao tác kéo thả), khiến Claude Code không có đủ dữ kiện để khoanh vùng đúng.
Giải pháp: Bổ sung lại bước tái hiện chi tiết hơn (màn nào, thao tác theo đúng thứ tự nào, kết quả mong đợi so với kết quả thực tế) rồi chạy lại /speckit-bug-assess — chẩn đoán chính xác phụ thuộc trực tiếp vào chất lượng mô tả tái hiện.
Lỗi: Chạy /speckit-bug-assess hoặc /speckit-bug-fix nhưng Claude Code báo không nhận diện được slash command.
Nguyên nhân: Chưa chạy specify extension add bug ở Bước 12, hoặc đã chạy nhưng vẫn dùng phiên Claude Code cũ mở từ trước đó nên chưa nạp lại slash command mới.
Giải pháp: Chạy specify extension add bug tại thư mục project (D:\lab-codekids-blocks) nếu chưa chạy, sau đó thoát phiên Claude Code hiện tại (/exit) và chạy lại claude để nạp lại toàn bộ slash command.

Dọn dẹp resource

Bài lab này không tạo resource cloud tính phí. Chỉ cần dừng container MySQL khi tạm nghỉ giữa các buổi thực hành: 
cd D:\lab-codekids-blocks
docker compose down

Có thể commit toàn bộ thay đổi (bao gồm .specify/, specs/, và code tính năng lõi) vào Git để lưu lại minh chứng cho cả quy trình SDD đã thực hiện. Giữ nguyên project để tiếp tục ở Chapter 7 — triển khai lên Vercel và TiDB.
