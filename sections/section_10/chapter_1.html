10. Phát triển phần mềm với Spec-Kit Framework / Spec-Driven Development (SDD) là gì

Giới thiệu

Spec-Driven Development (SDD) là phương pháp phát triển phần mềm trong đó bản đặc tả (specification) không còn là tài liệu viết một lần rồi bỏ quên, mà trở thành artifact thực thi được (executable artifact) — nguồn chân lý (source of truth) mà cả AI agent (như Claude Code) và con người cùng đọc trực tiếp để sinh ra kế hoạch kỹ thuật, task, và cuối cùng là code. Cách làm truyền thống thường xem spec chỉ là tài liệu tham khảo ban đầu: sau khi code xong, spec nhanh chóng lỗi thời vì không ai cập nhật lại. SDD đảo ngược thứ tự ưu tiên đó — spec luôn phải đúng trước, code là kết quả sinh ra từ spec, không phải ngược lại.

Các tính năng chính

  • Đặc tả (spec) được viết dưới dạng có cấu trúc, rõ ràng đến mức AI agent có thể đọc và "thực thi" trực tiếp — không chỉ là văn bản mô tả chung mà con người mới hiểu được.
  • Mọi giai đoạn tiếp theo (kế hoạch kỹ thuật, chia task, code) đều trace ngược lại được spec ban đầu — biết chính xác dòng yêu cầu nào sinh ra đoạn code nào.
  • Khi yêu cầu thay đổi, User cập nhật spec trước, sau đó lan toả xuống plan/task/code — tránh tình trạng code và tài liệu lệch nhau dần theo thời gian.
  • Giảm rủi ro "vibe coding" — code sinh ra tuỳ tiện theo cảm tính của từng lần prompt, không có cơ sở đối chiếu khi cần kiểm tra lại đúng/sai.
  • Phù hợp để làm việc cùng AI coding agent ở quy mô lớn hơn một vài prompt rời rạc — giữ ngữ cảnh nhất quán xuyên suốt cả một tính năng, thậm chí cả dự án.

Cách làm truyền thống: spec chỉ là điểm khởi đầu, dần lỗi thời vì code thay đổi mà không quay lại cập nhật. SDD: spec luôn ở vị trí trung tâm, mọi thay đổi đều bắt đầu từ việc cập nhật spec rồi lan toả xuống plan → task → code, khép vòng bằng bước đối chiếu (convergence).

Use Cases

Phát triển tính năng có kiểm soát

Thay vì prompt rời rạc "làm cái này, sửa cái kia", toàn bộ tính năng được đặc tả rõ ràng trước, giảm rủi ro AI hiểu sai ý định giữa các lần trao đổi.

Làm việc nhóm với AI agent

Nhiều người (hoặc nhiều AI agent khác nhau) cùng tham chiếu một spec duy nhất, tránh tình trạng mỗi người hiểu yêu cầu theo một cách.

Refactor/thay đổi lớn cần đối chiếu lại

Khi cần chứng minh một thay đổi lớn vẫn đáp ứng đúng yêu cầu ban đầu, spec đóng vai trò checklist để đối chiếu (convergence).

Thông tin bổ sung

SDD không thay thế hoàn toàn quy trình Explore → Plan → Code → Verify đã học ở Section 4 — có thể xem SDD là một phiên bản có cấu trúc và ghi lại thành file của quy trình đó, phù hợp khi tính năng đủ phức tạp để cần một bản đặc tả rõ ràng trước khi bắt tay vào code. Với các thay đổi rất nhỏ (sửa 1-2 dòng, fix lỗi đơn giản), quy trình prompt trực tiếp như ở Section 4 vẫn nhanh và hợp lý hơn.

Lưu ý: Chương tiếp theo sẽ giới thiệu Spec-Kit — công cụ mã nguồn mở cụ thể của GitHub giúp áp dụng triết lý SDD vào thực tế thông qua CLI specify và các slash command /speckit.* trong Claude Code.
