Phần 2: Viết CLAUDE.md định nghĩa quy tắc làm việc

  1. Bước 5: Yêu cầu Claude Code sinh file CLAUDE.md

    Liệt kê đầy đủ các mục cần có trong prompt — CLAUDE.md càng rõ ràng, cụ thể thì Claude Code càng tuân thủ chính xác ở các task sau này.

    Tạo file CLAUDE.md ở thư mục gốc project, định nghĩa quy tắc làm việc cho Claude Code trong toàn bộ dự án này. Nội dung gồm các mục sau:

1. Giới thiệu ngắn gọn cấu trúc project (docs/api-spec, docs/mockup, plans/backend, plans/frontend, plans/infra, prisma/, src/).
2. Các command npm thường dùng: npm run dev (start dev server), npm run build (build production), npm run lint (chạy ESLint), và các lệnh Prisma liên quan (migrate dev, studio).
3. Version cố định của stack: Next.js, React (React Compiler bật), TypeScript (strict mode), Tailwind CSS, Prisma — lấy đúng version đang có trong package.json của project hiện tại.
4. Kiến trúc App Router: toàn bộ source code nằm trong /src, root layout tại src/app/layout.tsx, không dùng Pages Router, TypeScript strict mode bắt buộc không được dùng any nếu không giải thích lý do.
5. Nơi lưu tài liệu: input mockup nằm ở /docs/mockup/, API spec OpenAPI 3.0 nằm ở /docs/api-spec, kế hoạch (plan) nằm ở /plans/backend, /plans/frontend, /plans/infra tương ứng.
6. Nguyên tắc thiết kế database dùng Prisma: mọi thay đổi schema phải qua migration, không sửa tay database, đặt tên model PascalCase số ít, field camelCase, luôn có createdAt/updatedAt, không xoá migration đã áp dụng.
7. Quy trình bắt buộc Explore → Plan → Code → Verify
Rule chung:
   - Explore: đọc code, hiểu cấu trúc, không sửa file.
   - Plan: đề xuất kế hoạch chi tiết, User đọc và duyệt trước khi Code. Các file plan (ten_task.md) phải liệt kê các hạng mục thực hiện theo dạng gạch đầu dòng gồm Thêm File, Sửa file, Xóa file.
   - Code: thực thi thay đổi đúng theo kế hoạch đã duyệt.
   - Verify: build, chạy test/lint, xem lại git diff để xác nhận thay đổi đúng như mong đợi.
   - Mỗi file plan phải có checklist dạng "- [ ] tên task", Claude Code phải tick "- [x]" sau khi hoàn thành từng task tương ứng.
   - Mỗi file phải có danh sách các test case (nếu có) để User kiểm tra sau khi Code xong.
Rule riêng cho 3 loại task:
   - Frontend/Screen: đọc mockup trong docs/mockup trước khi Plan, nếu user có chỉ định mockup cho màn hình, chỉ đọc đúng mockup cần thiết, ghi plan vào plans/frontend/.md.
   - Backend/API/Database: nếu chưa có API spec thì phải đề xuất OpenAPI spec ghi vào docs/api-spec trước, chờ duyệt rồi mới Plan; ghi plan vào plans/backend/.md.
   - Infra: ghi plan vào plans/infra/.md, không tự ý apply lên môi trường thật khi chưa được xác nhận ở bước Plan.

Sau khi viết xong, đọc lại toàn bộ nội dung CLAUDE.md một lượt và tóm tắt cho tôi các điểm chính.

    Nội dung dưới đây là ví dụ tham khảo cho những gì Claude Code nên sinh ra ở Bước 5 — dùng để đối chiếu..

## Cấu trúc project
- docs/api-spec/ — OpenAPI 3.0 spec cho từng API
- docs/mockup/<ten-man-hinh>/ — mockup do user cung cấp trước khi lên plan
- plans/backend/, plans/frontend/, plans/infra/ — kế hoạch do Claude Code tạo, chờ duyệt
- prisma/ — schema.prisma, migrations
- src/ — toàn bộ source code (App Router)

## Command thường dùng
- npm run dev — chạy dev server (localhost:3000)
- npm run build — build production
- npm run lint — chạy ESLint
- npx prisma migrate dev --name <mo-ta> — tạo & áp dụng migration
- npx prisma studio — xem/sửa data trực quan

## Version stack
- Next.js 15.x (App Router) · React 19 (React Compiler bật)
- TypeScript 5.x — strict: true bắt buộc
- Tailwind CSS 4.x · Prisma ORM 6.x

## Kiến trúc App Router
- Toàn bộ source nằm trong /src (app/, components/, lib/, types/, data/, services/, constants/, context/)
- Root layout: src/app/layout.tsx
- Không dùng Pages Router. Không dùng any nếu không giải thích lý do bằng comment.

## Nguyên tắc thiết kế database (Prisma)
- Mọi thay đổi schema phải qua migrate dev, không sửa tay database
- Model PascalCase số ít, field camelCase, luôn có createdAt/updatedAt
- Không xoá migration đã áp dụng — tạo migration mới để sửa

## Quy trình bắt buộc: Explore → Plan → Code → Verify
1. Explore trước, không sửa file khi đang explore
2. Ghi plan ra đúng thư mục /plans tương ứng, có checklist - [ ]
3. Chờ user duyệt plan trước khi Code
4. Verify: build + lint trước khi báo hoàn thành
5. Tick - [x] vào plan sau khi hoàn thành từng task

### Rule riêng — Frontend/Screen
- Đọc mockup trong docs/mockup/<ten-man-hinh> trước khi Plan (nếu có)
- List up all components, props, state, data flow, edge cases.
- List logic xử lý, query params, validation, error handling, và các test case.
- Ghi plan vào plans/frontend/<ten-man-hinh>.md

### Rule riêng — Backend/API/Database
- Nếu chưa có API spec, đề xuất OpenAPI spec ghi vào docs/api-spec trước, chờ duyệt
- List up all components, props, state, data flow, edge cases.
- List logic xử lý, query params, validation, error handling, và các test case.
- Ghi plan vào plans/backend/<ten-feature>.md
- Thay đổi schema Prisma → tạo migration ngay trong cùng task

### Rule riêng — Infra
- Ghi plan vào plans/infra/<ten-feature>.md
- Không tự ý apply lên môi trường thật khi chưa được xác nhận rõ ràng ở bước Plan

## Không làm
- Không tự ý đổi cấu trúc thư mục đã định nghĩa ở trên
- Không cài thêm package ngoài phạm vi task mà không hỏi trước
Vì sao nên chia rule theo Frontend / Backend / Infra thay vì viết chung một quy trình? Mỗi loại task có input và rủi ro khác nhau — Frontend cần đọc mockup, Backend cần thống nhất API spec trước khi code (tránh FE/BE hiểu sai hợp đồng dữ liệu), Infra có rủi ro cao nhất vì có thể ảnh hưởng tài nguyên thật. Rule riêng giúp Claude Code phản ứng đúng theo ngữ cảnh thay vì áp dụng một quy trình cứng nhắc cho mọi tình huống.

Phần 3: Thử nghiệm áp dụng CLAUDE.md qua một tính năng mới

  1. Bước 7: Giao một tính năng mới, không nhắc lại quy trình

    Vì CLAUDE.md đã được Claude Code tự động nạp vào context, prompt lần này chỉ cần mô tả tính năng — không cần lặp lại yêu cầu "hãy viết plan trước" hay "ghi vào file .md" như các bài lab trước.

    Thêm tính năng lọc danh sách khoản chi tiêu trên trang chủ theo category và khoảng thời gian (từ ngày - đến ngày). Kết quả lọc hiển thị lại bảng danh sách và tổng số tiền của các khoản đang được lọc.
  2. Bước 8: Quan sát Claude Code tự tạo file plan đúng vị trí

    Vì đây vừa có phần API (backend) vừa có phần giao diện (frontend), quan sát xem Claude Code có tách plan thành 2 file đúng theo rule đã định nghĩa hay không.

    dir plans/backend, plans/frontend
plans/backend/filter-expenses.md
plans/frontend/dashboard-filter.md
    Nếu Claude Code không tạo file plan hoặc đặt sai thư mục: đây là dấu hiệu rule trong CLAUDE.md chưa đủ rõ ràng. Yêu cầu Claude Code dừng lại, không code trực tiếp, và bổ sung câu rõ ràng hơn vào CLAUDE.md — ví dụ: "Bắt buộc ghi plan ra file .md trước khi sửa bất kỳ file code nào, kể cả tác vụ nhỏ." Đây chính là bước tự hoàn thiện quy tắc dự án theo kinh nghiệm thực tế.
  3. Bước 9: Đọc và duyệt plan

    Mở 2 file plan vừa tạo, kiểm tra checklist các task, chỉnh sửa trực tiếp trong file nếu muốn thay đổi phạm vi (ví dụ thêm/bớt điều kiện lọc), sau đó xác nhận cho Claude Code tiếp tục thực thi (Accept Edits mode hoặc trả lời "OK, thực hiện theo plan này").

  4. Bước 10: Verify — build, lint và kiểm tra checklist 
    npm run lint
npm run build

    Mở lại 2 file plan, xác nhận các dòng checklist đã được Claude Code tự tick - [x] tương ứng với phần đã hoàn thành. Sau đó chạy dev server và kiểm tra tính năng lọc trên trình duyệt.

    npm run dev

✅ Kết quả mong đợi

Project có cấu trúc thư mục rõ ràng theo database/, docs/, plans/, prisma/, src/. File CLAUDE.md tồn tại ở root và được Claude Code tuân thủ khi thực hiện task mới: tự tạo file plan đúng thư mục (plans/backend, plans/frontend), tự tick checklist sau khi hoàn thành, và tính năng lọc khoản chi tiêu hoạt động đúng trên http://localhost:3000.

Troubleshoot

Lỗi: Claude Code code thẳng vào file mà không ghi plan trước, dù CLAUDE.md đã yêu cầu.
Nguyên nhân: Rule trong CLAUDE.md nằm rải rác, dùng từ ngữ chung chung ("nên", "cố gắng") thay vì bắt buộc, hoặc file CLAUDE.md quá dài khiến rule quan trọng bị "loãng".
Giải pháp: Dùng từ khoá dứt khoát ("bắt buộc", "luôn luôn", "không được") cho các rule quan trọng, đặt quy trình Explore → Plan → Code → Verify ở vị trí dễ thấy (đầu file hoặc heading riêng), tránh nhét quá nhiều thông tin không liên quan vào cùng một file.
Lỗi: Claude Code tạo file plan nhưng ghi sai thư mục (ví dụ để chung plans/backend và plans/frontend vào một file).
Nguyên nhân: Prompt giao task không tách rõ phần nào là backend/API, phần nào là frontend/UI.
Giải pháp: Với các tính năng liên quan cả hai (full-stack), có thể chủ động yêu cầu Claude Code "tách plan backend và frontend thành 2 file riêng theo đúng CLAUDE.md" ngay trong prompt giao task, thay vì chờ Claude Code tự suy luận.
