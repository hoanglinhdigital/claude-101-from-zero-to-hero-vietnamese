6. Claude cho Tester / QA / Lab - Viết bug report hoàn chỉnh
Bài lab này dùng lại đúng bug đã phát hiện qua test tự động ở Chapter 5 (amount <= 0 vẫn được lưu) làm ví dụ thực hành. Nếu bạn chưa làm Chapter 5, vẫn có thể thực hành bình thường với mô tả lỗi mẫu dưới đây.

Mục tiêu

  • Biết cách đưa một mô tả lỗi ngắn gọn, thô cho Claude và yêu cầu soạn bug report đầy đủ theo cấu trúc chuẩn đã học ở Chapter 3.
  • Đối chiếu input thô ban đầu với output bug report hoàn chỉnh để thấy rõ giá trị Claude thêm vào.
  • Biết tự chỉnh sửa, bổ sung những phần Claude còn thiếu hoặc suy diễn sai (đặc biệt là mức độ ưu tiên/severity).

Từ một câu mô tả lỗi ngắn gọn, Claude chuẩn hoá thành bug report đầy đủ theo cấu trúc chuẩn đã học ở Chapter 3, sẵn sàng đưa vào bug tracker để Developer tiếp nhận.

Yêu cầu trước khi bắt đầu

  • Claude.ai hoặc Claude Code CLI đã cài đặt, đăng nhập thành công.
  • Đã đọc Chapter 3 — cấu trúc bug report chuẩn (Tiêu đề, Mô tả, Môi trường, Bước tái hiện, Kết quả mong đợi, Kết quả thực tế, Severity, Ghi chú bổ sung).
  • (Khuyến nghị) Đã hoàn thành Chapter 5 để có ngữ cảnh thật từ chính bug vừa phát hiện.

Các bước thực hành

Phần 1: Chuẩn bị mô tả lỗi thô

  1. Bước 1: Viết mô tả lỗi ngắn gọn như một Tester thực tế thường ghi chú nhanh

    Mô tả mẫu dùng cho bài lab này — đúng bug đã thấy ở Chapter 5 khi test API POST /api/expenses:

    tạo chi tiêu số âm mà vẫn lưu được

Phần 2: Yêu cầu Claude soạn bug report đầy đủ

  1. Bước 2: Gõ prompt đưa mô tả thô kèm bối cảnh, yêu cầu soạn bug report theo đúng cấu trúc chuẩn 
    Tôi vừa phát hiện lỗi sau khi test app Quản lý chi tiêu (Expense Management):
"tạo chi tiêu số âm mà vẫn lưu được"

Bối cảnh thêm: lỗi xảy ra khi gọi API POST /api/expenses (Next.js), môi trường local (Windows 11, Node.js 18, MySQL 8.0 qua Docker container). Tôi gửi request với amount = -100000, các field khác hợp lệ (title, categoryId, spentAt), server trả về status 200/201 và lưu bản ghi vào database thay vì từ chối.

Hãy soạn giúp tôi một bug report đầy đủ theo cấu trúc chuẩn: Tiêu đề, Mô tả, Môi trường, Bước tái hiện, Kết quả mong đợi, Kết quả thực tế, Mức độ ưu tiên/Severity (kèm giải thích ngắn vì sao chọn mức đó), Ghi chú bổ sung.
  2. Bước 3: Đọc và đối chiếu bug report Claude soạn ra

    Bảng dưới đây là ví dụ tham khảo cho output đầy đủ Claude nên soạn ra ở Bước 2 — dùng để đối chiếu với kết quả thực tế của bạn.

    TrườngNội dung
    Tiêu đềAPI POST /api/expenses chấp nhận amount âm, không validate trước khi lưu database
    Mô tảKhi gửi request tạo khoản chi tiêu với số tiền âm, hệ thống vẫn lưu thành công vào database thay vì từ chối theo đúng requirement (số tiền phải > 0). Điều này khiến số liệu tổng chi tiêu hiển thị cho người dùng bị sai lệch.
    Môi trườngWindows 11, Node.js 18.x, Next.js (App Router), MySQL 8.0 (Docker container expense-mysql), dev server local http://localhost:3000.
    Bước tái hiện 1. Khởi động dev server (npm run dev).
    2. Gửi POST http://localhost:3000/api/expenses với body { "title": "Test", "amount": -100000, "categoryId": 1, "spentAt": "2026-07-09" }.
    3. Quan sát response và kiểm tra dữ liệu trong bảng Expense.
    Kết quả mong đợiServer trả về status 400 kèm message lỗi rõ ràng ("Số tiền phải lớn hơn 0"), không tạo bản ghi mới.
    Kết quả thực tếServer trả về status 200/201, bản ghi được lưu vào bảng Expense với amount = -100000.
    Mức độ ưu tiên/SeverityHigh — ảnh hưởng trực tiếp đến tính đúng đắn của số liệu tài chính hiển thị (dashboard tổng chi tiêu sẽ sai), nhưng chưa phải Critical vì không gây crash hệ thống hay mất dữ liệu người dùng đã có.
    Ghi chú bổ sungPhát hiện qua bộ test tự động (xem Chapter 5). Gợi ý hướng fix: thêm validate amount > 0 tại API route app/api/expenses/route.ts trước khi gọi Prisma create.

Phần 3: Đối chiếu giá trị Claude thêm vào

Input thô (1 câu)

"tạo chi tiêu số âm mà vẫn lưu được"

Không có bước tái hiện, không có môi trường, không có mức độ ưu tiên — chưa đủ để Developer bắt tay vào fix ngay.

Output bug report (8 trường)

Tiêu đề rõ nghĩa · Mô tả đầy đủ · Môi trường cụ thể · 3 bước tái hiện · Kết quả mong đợi vs thực tế · Severity kèm lý do · Ghi chú hướng fix.

Developer có thể tái hiện và bắt đầu fix ngay, không cần hỏi lại Tester.

✅ Kết quả mong đợi

Bug report do Claude soạn có đủ 8 trường chuẩn, đủ chi tiết để một Developer chưa từng thấy lỗi này có thể tái hiện và bắt đầu fix mà không cần hỏi lại Tester.

Troubleshoot

Lỗi: Claude tự suy diễn sai môi trường hoặc phiên bản phần mềm.
Nguyên nhân: Input ban đầu không cung cấp đủ bối cảnh, Claude phải tự đoán để điền vào trường "Môi trường".
Giải pháp: Luôn bổ sung bối cảnh thật (OS, version, môi trường local/staging/production) ngay trong prompt như ví dụ ở Bước 2, không để Claude tự đoán.
Lỗi: Mức độ ưu tiên/Severity Claude đề xuất không khớp với đánh giá thực tế của team.
Nguyên nhân: Claude không biết đầy đủ tác động nghiệp vụ hoặc ưu tiên hiện tại của dự án.
Giải pháp: Luôn coi severity Claude đề xuất là gợi ý — Tester/Lead QA là người quyết định mức cuối cùng trước khi gửi bug tracker.
Lỗi: Bug report thiếu bước tái hiện cụ thể, chỉ mô tả chung.
Nguyên nhân: Input ban đầu không có request/response mẫu.
Giải pháp: Bổ sung ví dụ body request (JSON) và response thực tế nhận được vào prompt, như đã làm ở Bước 2.
